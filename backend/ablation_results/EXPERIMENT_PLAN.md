# 疊加與消融實驗規劃(2026-11-05)

這份文件是**唯一的依據**:疊加實驗、消融實驗、評分、紀錄、重跑流程都以這裡為準。簡報、README、程式註解與這裡不一致時,以這裡為準,並修正另一邊。要改規劃,先改這份文件、再改其他地方,並在文件最後的「變更紀錄」寫明日期與原因。

## 0. 為什麼重新規劃

2026-11-05 以前的疊加實驗(步驟 0 到 3)與消融實驗各自定義零件,出現過三種不一致:

1. 疊加的步驟 1 把「系統語料庫」只取了每筆的 `content` 文字,丟掉結構化欄位、整頁展開與標籤。語料庫被拆成兩半,後面的元件拿不到它們。
2. 消融的「領域知識」同時清掉詞彙表、公式庫、會計慣例、題型提示,卻保留財年判斷與提示詞通用部分;疊加則把詞彙表放進分類器。兩邊的零件邊界不同。
3. 拆題器的輸出上限(`max_completion_tokens`)寫死 2000。gpt-5 系列的推理 token 會用掉整個額度,約 6% 的呼叫回傳空內容,系統不報錯、悄悄退回規則拆題。基準與所有舊實驗都受影響,但沒有留下記錄,無法得知哪幾題。

因此:舊的疊加(185、175、188、196 / 300)與舊消融結果**封存為第一版**(分支保留,簡報另存 v1),**不與新結果混用**。新的規劃在修好上限之後,全部重跑。

## 1. 固定條件(所有實驗相同)

- 模型:gpt-5-mini(推理型,不傳 temperature);每題單檔上傳(只載入該題自己的財報),題目共 300 題 = 訓練集 150(`original`)+ 獨立測試集 150(`outsample`)。
- 每個設定只跑一次;輪與輪之間的雜訊約 7 題,差距小於此不下結論。
- 語料庫來源:`backend/tests/original_corpus_cache.pkl`、`outsample_corpus_cache.pkl`(系統解析好的語料庫,含表格重建與 MinerU 修復段落);純文字對照用 `*_clean_corpus_cache.pkl`。這四個檔案在整個重跑期間**不得重建**。
- 4 個程序分片同時跑(`--shard K/4`),以 `--out` 續跑:已完成的題**不重跑、不覆蓋**。
- 錯誤處理:任何一題回傳錯誤、空答案、或系統自己的「備援合成答案」(`_synthesize_*_concise`,表示 LLM 呼叫失敗),**一律視為未完成,補跑**,不拿去評分。
- 用量:每次執行都存 `usage_ledger`(應用內帳本在這類執行常為 0,所以另外從每題結果的 token 欄位彙整)。
- 啟動規矩:**每一次啟動前**(含續跑、重跑)先告訴使用者要跑什麼、預計多久、約多少 token,等到使用者在同一輪說好才啟動。使用者暫停時要殺掉整個程序樹。

## 2. 前置:dev 修正(只有這一項進 dev)

`backend/app/agent/decomposer.py` 兩處(`_llm_decompose` 與 `suggest_narrative_topic_query`)對推理型模型的 `max_completion_tokens` 由 2000 改為 16000。

- 依據:步驟 2、3 不設上限時 354 次呼叫的輸出長度(含推理):中位數約 930、p95 約 2200 到 2400、最大 5976;現行 2000 上限約截掉 6%。
- 不改行為:LLM 拆題仍然回傳空時,照現狀退回規則拆題(不報錯、不重試;同上限重試結果相同)。
- 非推理型模型維持 768 與 100。
- 其他 LLM 呼叫點只有答案生成一處(`llm_client.py`),沒有輸出上限,不受影響。驗證、PoT、改寫查詢不呼叫 LLM。
- **所有實驗開關(下面第 7 節)都不進 dev**,只在實驗分支。

## 3. 零件清單(7 個元件,疊加與消融共用)

| 元件 | 包含 | 程式位置 | 被誰用到 |
|---|---|---|---|
| C1 語料庫 | 表格逐列重建、結構化欄位(公司、表格名稱、期間、章節、頁碼、片段類型、父頁面)、整頁展開、`- [公司 / 表格名稱]` 標籤、每塊顯示上限 4000 字或 30 列 | parser、table_parser、table_repair、`llm_client._evidence_display_text`/`_truncate_evidence_content` | 檢索、顯示 |
| C2 答案提示詞 | 系統訊息;開頭「You are a professional financial analysis assistant」;原則 ① 到 ④;會計慣例;5 種題型提示(排名、加速/減速、客戶集中、已發生成本、(去)槓桿);財年與欄位判斷;輸出格式;檢查清單(含 3 條 CRITICAL) | `llm_client.generate_answer`、`accounting_conventions`、`answer_directives` | 模型 |
| C3 題型分類器 + 詞彙表 | 分類器輸出(回答模式、檢索策略、目標指標、年份、公司、報表類型提示、題型、認知任務、分類器自己的查詢句);詞彙表(`QUESTION_METRICS`、`LINE_ITEM_ALIASES`、`COMPOSITE_LINE_ITEM_ALIASES`、`LINE_ITEM_STATEMENT`);提示詞的 Answer Mode 與 Routing Reason 兩行;公司名與財報對齊 | question_classifier、financial_vocabulary、orchestrator `_match_entity_to_corpus` | 拆題、檢索、PoT |
| C4 拆題器 + 公式庫 | 命中公式庫的題用公式變數查詢(不呼叫 LLM 拆題);否則 LLM 拆子問句(附問題自帶公式)失敗則規則拆題;非數值題用分類器查詢句;補查詢:問題原文(數值題無公式、不需計算題型、敘述題)、敘述主題查詢、隱含前一年 | decomposer、financial_formula_library、orchestrator `_plan_queries`、pot_reasoner 的 `is_no_calculation_question` 與 `_with_implied_trend_year` | 檢索、PoT、重試 |
| C5 檢索 | 系統檢索器評分(BM25×0.7 + 關鍵字重疊×0.3);8 條加權(見下);每個子問句各搜一次(一般 top 5、敘述 top 15)、排除已取過的、跳過已有的(指標、年度)、每步以子問句自己的文字重算報表類型提示、去重(同 id 取最高分)、限定同公司;配額(每個子問句保證 2 塊、原問題搜尋保證 5 塊)取視窗 30,再取 16 給模型 | lexical_retriever、evidence_selection、orchestrator 迴圈 | 提示詞 |
| C6 PoT | 規則式抽數與寫程式、沙盒計算、合理性檢查、特殊調整(營運資金、速動比率、EBIT、存貨週轉等);視窗 30 送 PoT;被用到的證據釘進送模型的 16 塊;提示詞的 Computed value 段與原則 ⑤ | pot_reasoner、sandbox | 提示詞 |
| C7 驗證與重試 | Tri-Check 三項檢查;失敗型態對應重試計畫(擴大、鎖定、改寫);最多 3 輪;提示詞的 Verification summary 行 | verifier、refiner、orchestrator `_plan_retry` | 重試、提示詞 |

8 條加權:`company_match`(2.0/1.8/1.2/0.4/0.05)、`line_item_match`(1.5)、`total_row_boost`(1.3)、`inventory_composition_boost`(3.0)、`preferred_filing_year_boost`(1.3)、`low_confidence_column_penalty`(0.5)、`year_match_boost`(1.4)、`statement_type_hint_boost`(1.5)。其中 `line_item_match` 與 `statement_type_hint_boost` 依賴 C3 的詞彙表與報表類型提示。

提示詞各段落由哪個元件負責(疊加時隨該元件加入):

| 段落 | 元件 |
|---|---|
| 系統訊息、開頭一句、原則 ① 到 ④、輸出格式、檢查清單、會計慣例、題型提示、財年判斷、證據段標題 | C2 |
| `Answer Mode`、`Routing Reason` 兩行 | C3 |
| `Computed value` 段與原則 ⑤ | C6 |
| `Verification summary` 行 | C7 |

不屬於任何元件、所有實驗一致的:輸入題目、單檔、gpt-5-mini、答案不後處理。

## 4. 疊加實驗(每步只加一個元件)

步驟 N 的設定 = 元件 C1 到 C(N) 開、其餘全部關。步驟 0 是獨立的 Naive RAG。最後一步 = 完整系統 = 基準。

| 步 | 加入 | 該步檢索 | 該步提示詞 | 該步模型看到 |
|---|---|---|---|---|
| 0 | Naive RAG | 純文字 1000 字切塊(步長 800)、`rank_bm25` 預設參數、小寫、空白切詞;問題原文單一查詢;取 16 塊 | `Context:\n{16塊}\n\nQuestion: {問題}`;無系統訊息 | 純文字 |
| 1 | C1 語料庫 | 同步驟 0 的 rank_bm25,但在系統語料庫的片段 `content` 上檢索,取 16 塊;同頁可重複出現(系統本來就如此) | 步驟 0 格式,但證據改為 `- [公司 / 表格名稱] {整頁}` | 整頁加標籤 |
| 2 | C2 答案提示詞 | 同步驟 1 | 系統提示詞:題目在前,證據在後;題型提示與財年判斷掃描的範圍 = 送給模型的證據;沒有 Answer Mode、Computed value、Verification summary 三段,原則 ⑤ 不放 | 系統提示詞 |
| 3 | C3 分類器 + 詞彙表 | 數值題:問題原文;說明題:問題原文 + 分類器自己的查詢句;所有查詢串成一個字串給 rank_bm25 取 16 塊 | 加 Answer Mode 與 Routing Reason | 同上 |
| 4 | C4 拆題器 + 公式庫 | 查詢 = 規劃出的全部子問句(含公式變數查詢、問題原文、敘述主題查詢、隱含前一年),去重後串成一個字串給 rank_bm25 取 16 塊 | 同步驟 3 | 同上 |
| 5 | C5 檢索 | 換成系統檢索器、8 條加權、每子問句各搜一次、配額、視窗 30 取 16;題型提示掃描的範圍擴為視窗 30 | 同步驟 3 | 同上 |
| 6 | C6 PoT | 同步驟 5;視窗 30 送 PoT | 加 Computed value 與原則 ⑤;只跑一輪(沒有驗證與重試) | 同上 |
| 7 | C7 驗證與重試 | 同步驟 5,重試時依失敗型態再檢索 | 加 Verification summary;最多 3 輪 | 完整系統 |

已知的順序相依(論文要寫):
- 步驟 3 的分類器單獨作用很小:此時只影響說明題的查詢句與提示詞兩行;它的報表類型提示與目標指標,要到步驟 5 的加權、步驟 6 的 PoT 才派上用場。
- 步驟 4 產生的「問題自帶公式」要到步驟 6 才被 PoT 使用。
- 步驟 5 以前的 `line_item_match` 與 `statement_type_hint_boost` 不存在;步驟 3 起詞彙表在,所以它們在步驟 5 一加入就生效。
- 公式庫關閉時(消融),PoT 與重試也失去公式;開啟時它同時服務檢索、PoT、重試,這是設計,不是漏洞。

## 5. 消融實驗(完整系統一次拿掉一個元件,共 8 次)

每一列拿掉的 = 疊加那一步加進去的**全部**東西;其餘照完整系統。

| 列 | 拿掉 | 換成什麼 | 連帶效應(論文要寫) |
|---|---|---|---|
| 1 | C1 語料庫 | 純文字 1000 字切塊,沒有欄位、標籤、整頁展開;其餘管線不變 | 8 條加權因欄位消失而部分失效 |
| 2 | C2 答案提示詞 | 步驟 0 的簡短提示詞(`Context` 與 `Question`,無系統訊息),但 Computed value 與 Verification summary 兩段在系統有產生時照常附在證據後 | 題型提示、會計慣例、財年判斷、原則一併消失 |
| 3a | C3 分類器 + 詞彙表(強制數值題路徑) | 所有題目走數值題路徑;檢索策略固定 HYBRID;報表類型提示清空;詞彙表四張表清空 | 檢索的科目比對、PoT 的科目對應也因詞彙表清空而失效 |
| 3b | 同上(強制說明題路徑) | 所有題目走說明題路徑,其餘同 3a | 同上 |
| 4 | C4 拆題器 + 公式庫 | 不拆題,只用問題原文(說明題另加分類器的查詢句);公式庫關閉(`detect_formula` 回傳 None) | PoT 與重試也失去公式,差距可能最大 |
| 5 | C5 檢索 | `rank_bm25`、所有查詢串成一個、取 16 塊;沒有加權、配額、視窗 30 | 題型提示掃描範圍縮回 16 塊 |
| 6 | C6 PoT | 拿掉 PoT(所有題視為不需計算,Computed value 段與原則 ⑤ 不出現) | |
| 7 | C7 驗證與重試 | 一律接受,不重試,沒有 Verification summary 行 | |

分類器列保留強制數值、強制說明兩次,因為單一方向的強制會偏向某一類題型。

## 7. 實作方式與離線驗證

- 兩個實驗**使用同一份程式、同一組開關**:在新的實驗分支 `experiment/stack-ablation`(從修好的 dev 開)為每個元件加環境變數開關(預設全開 = 完整系統)。疊加步驟 N = 把 C(N+1) 以後的開關全部關;消融 = 只關一個。這樣最後一步就是系統本身,不會因為另寫一份程式而不一致。
- 步驟 0 維持獨立的 `backend/clean_baseline/run.py`。
- **開跑前的離線驗證(不呼叫 API,不花額度)**:對固定的三題(一題命中公式庫的數值題、一題未命中的數值題、一題敘述題)在 15 個設定下各印出查詢、取回的片段 id、完整提示詞,存檔;相鄰兩個疊加步驟的輸出差異必須**只有該步驟加入的東西**。核對不過就不啟動。
- 另跑一次確認:全部開關全開時,輸出與 dev 未改開關前的完整系統逐字相同。
- 每個開關都要有單元測試證明「關掉時完全等同沒有這個元件」。

## 8. 評分

- 標籤 C(正確)、S(小誤差)、P(部分正確)、W(錯誤)。規則與 22 項邊界情形決策表以 `backend/ablation_results/baseline/README.md` 為準,本文件不重複。
- 每一組 300 題逐題讀答案評分;判完後與**所有**已判過的組逐題比對(標籤不同的題、數字相近標籤不同的題),重讀後依決策表統一。
- 不用「答案含有標準答案的輸入數字」代替閱讀:要用答案自己寫的算式重算。
- 結果寫入單一一次提交:逐題標籤、摘要、README、用量。數字以讀完的標籤為準。

## 9. 紀錄與簡報

- 每個設定一個資料夾 `backend/ablation_results/<名稱>/`:合併後的 300 題答案、逐題標籤、`summary.json`、README(寫明開關設定與日期)、用量彙整;分片檔與日誌不留。
- 執行紀錄(分片輸出、帳本)放 `financial_agentic_rag_runs/`,並複製進結果資料夾。
- 簡報:第四章簡報只放這份規劃與已定案的結果;每完成一組才補對應頁面。第一版封存在 `https://claude.ai/artifact/6dpnAd62YVxQHFHoBWfsSy`(第四章)與 `https://claude.ai/artifact/86rWYGEyXzE6aYYxAW1gnc`(獨立測試集)。

## 10. 建議執行順序

1. 修 dev(第 2 節),測試,提交,重建各實驗分支。
2. 建立 `experiment/stack-ablation`,加開關與測試,離線驗證通過(第 7 節)。
3. 基準(= 步驟 7)。
4. 疊加步驟 1 到 6。
5. 消融 1 到 7。
6. 每組跑完立即評分、跨組比對、存檔、更新簡報。
換模型實驗(gpt-5-nano、gpt-4o-mini、Gemini 兩個、Claude)**不重跑**,結果沿用,論文註明它們的拆題器是舊上限。

## 11. 已知限制

- 單次執行、雜訊約 7 題;評分由 AI 助理依書面規則逐題判讀、作者複核,沒有獨立第二位評審。
- 疊加結果取決於加入順序,消融取決於其餘元件存在;兩者並列是為了互相對照,不能互相替代。
- 獨立測試集 150 題沒有一題要自己決定算法(公式庫相關效果在訓練集才明顯)。
- 舊的換模型實驗拆題器仍為 2000 上限。
